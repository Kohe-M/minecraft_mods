# Minecraft 26.3 の注意点

- 非難読化・Mojang 名
- 描画は `extract*` / `GuiGraphicsExtractor`、画面は `Minecraft.gui.screen()` / `gui.setScreen()`
- HUD を隠す（F1）のは `Minecraft.gui.hud.toggle()` / `isHidden()`。`Options.hideGui` はない
- `InputConstants.MOUSE_BUTTON_LEFT` は 1（GLFW の 0 ではない）。クライアントゲームテストの `pressMouse` もこれを使う
- チェストなどのブロックエンティティはチャンクのメッシュに入らず、`BlockEntityRenderDispatcher.tryExtractRenderState` で描画の状態を作る（Sodium も同じ）。明るさ（`lightCoords`）は本物のワールドから読み、`BlockEntityRenderer.shouldRender` は既定で 64 ブロックより遠いものを描かない
- エンティティの明るさは `EntityRenderer.getPackedLightCoords`（final）が本物のワールドから読む。描く距離は `Entity.shouldRender(DDD)`（当たり判定の 3 辺の平均 × 64 × エンティティの描画距離の設定。鶏で 32 ブロック）で、`EntityRenderer.shouldRender` が視錐台より先に見る
- いまのカメラの視錐台は `Minecraft.gameRenderer.mainCamera().getCullFrustum()`
- エンティティの種類の定数は `EntityTypes.SHEEP` など。`EntityType` にはなく、`EntityTypeIds` は `ResourceKey`
- 全チャンクの再構築は `Minecraft.levelExtractor.allChanged()`（F3+A と同じ）。`levelRenderer.invalidateCompiledGeometry` を直接呼ぶと、素の描画では再構築が予約されず何も描かれなくなる
- クライアントゲームテストの入力は、マウスのイベントに修飾キーを載せない。Shift の判定は `event.hasShiftDown()` ではなく `Minecraft.hasShiftDown()` を使う
- `GameRenderer.projectPointToScreen` はカメラの後ろの点も画面の中に写す。前後はカメラの向きとの内積で判定する
- `ClientLevel.hasChunk` は常に true を返す。クライアントがチャンクを持っているかは `getChunkSource().getChunk(x, z, ChunkStatus.FULL, false) != null` で見る
- ロケーターバーは、相手のチャンクが描画距離の外ならチャンクの位置、332 ブロックより遠いなら方角だけを送る（`LivingEntity.makeWaypointConnectionWith`）。サーバーで相手ごとの接続を管理するのは `ServerWaypointManager`。方角しかないデータから距離は分からない
- `ServerChunkCache.getChunkFuture(..., true)` が付ける札（`TicketType.UNKNOWN`）は 1 tick で外れ、生成が終わる前に捨てられることがある。非同期に読み込むときは `FLAG_CAN_EXPIRE_IF_UNLOADED` のない `TicketType` の札を付ける。時間は `ChunkHolder.isReadyForSaving`（生成の途中でない）になってから数えるので、FULL より前の状態まで（`ChunkLevel.byStatus`）の札でも外れる
- `IOWorker` は読み込みを保存より先に回す。読み込みを詰め続けると保存が進まず、書く前のチャンクがメモリに溜まる。読み込みは IO スレッド 1 本で展開・読み解きまで行うので、多く読むならリージョンファイルを自分で読む
- チャンクの生成の段階は STRUCTURE_STARTS・STRUCTURE_REFERENCES・BIOMES・TERRAIN（ノイズ・地表・洞窟をまとめたもの）・FEATURES の順。生成の仕事は `ChunkMap.worldgenTaskDispatcher`（`ChunkTaskDispatcher`）が `ChunkTaskPriorityQueue` に、チャンクのレベル（`ChunkHolder.getQueueLevel`）を段にして並べる。小さい段から 1 チャンクずつ取り出し、1 本の列（`ConsecutiveExecutor` の worldgen）で順に動かす。構造物と地物の配置はこの列の中で同期に動き、BIOMES と TERRAIN の中身だけが `Util.backgroundExecutor()`（コア数 − 1 本、ほかの仕事と共有）に出る。レベルが変わると `resortChunkTasks` が古いレベルの段から仕事を探して移す
- `ServerChunkCache.getChunkFuture` をメインスレッドから呼ぶと、そのチャンクができるまでメインスレッドで待つ（`managedBlock`）。待たずに頼むときは別のスレッドから呼ぶ（メインスレッドへのタスクになる）
- サーバーの遅れは `getNextTickTime()` と今の時刻の差では測れない（クライアントのゲームテストではいつも 0.5 秒ほど遅れて見える）。直近の数 tick にかかった実時間で測る
- ワールドから外れたチャンクの保存（`ChunkMap.processUnloads`）は、待ちが 2000 を超えた分と、tick の合間に時間が余っている間だけ進む。クライアントのゲームテストの内蔵サーバーは時間が余らない扱いなので、多くのチャンクを生成した後は 2000 個が保存待ちのまま残る（`pendingUnloads`）。テストではメモリにある方の状態も見る
- `CommandEncoder.writeToTexture` は呼ぶたびに重い。小さい範囲を何度も送らず、まとめて送る
- リージョンファイル（.mca）のヘッダーは 8 KiB。前半がチャンクごとの場所（0 はチャンクがない）、後半がチャンクを書いた時刻（秒）で、チャンクを書くたびに両方が書き直される。チャンクは変わったもの（`ChunkAccess.isUnsaved`）だけが書かれるので、時刻はチャンクの中身の版として使える
- チャンクが `ChunkMap.pendingUnloads` から外れてから、IO スレッドがファイルに書き終えるまでには間がある（ふつうは 1 秒もかからない）。その間、ファイルにはチャンクがないか古い中身のまま
- `ServerChunkCache.blockChanged` が呼ばれるのは、tick されているチャンク（`FullChunkStatus.BLOCK_TICKING` 以上）で、クライアントに知らせる変化（`UPDATE_CLIENTS`）だけ。コマンドで読み込んだだけのチャンクの変化は来ない。サーバーのブロックの変化をすべて知るには `LevelChunk.setBlockState`（変わらなければ null を返す）を見る
- `ServerChunkEvents.CHUNK_LOAD` / `CHUNK_UNLOAD` は FULL のチャンク（`LevelChunk`）だけ。生成の途中のチャンク（`ProtoChunk`）では呼ばれない。FULL のチャンクが弱い札で読み込まれているときの `ImposterProtoChunk` は `isUnsaved()` がいつも false なので、`getWrapped()` の方を見る
- 地形の密度の関数（`DensityFunction`）は `RandomState.getSampler` / `samplersWithContext(SamplerContext)` で `DensitySampler` にして使う。`DensityVolume`（大きさ・始点・刻み）を渡すと範囲をまとめて出せて、1 点ずつ（`sampleValue`）よりずっと速い。同じ範囲で何度も使う 2 次元のノイズは、`SamplerContext.builder().enableCaches()` の文脈なら使い回される（範囲が変わると捨てられる）。どのスレッドから呼んでもよい
  - `InterpolatedFunction`（地形の密度はこれで 4 × 8 × 4 ブロックおきに計算して間を埋める）は、刻みが区切りと違う範囲を渡すと、1 ブロック刻みで全部計算してから間引く。区切りに合わない刻みで広い範囲を出すと遅い。1 列だけ（大きさ 1 × 高さ × 1）なら、その列の角だけを計算する
  - `NoiseRouter` にあるのは気候（`temperature`・`vegetation`・`continents`・`erosion`・`depth`・`ridges`）と `chunkSurfaceLevel`・`finalDensity` だけ。`depth` は地表で 0、下ほど大きく、高さに比例する。`chunkSurfaceLevel` と `Aquifer.Config.surfaceLevel` は帯水層のための低めの見積もり（8 ブロック刻み）で、本物の地表より 10 ブロックほど低い
  - 地形の密度は地表より上で 1 倍、下で 4 倍に効く（`noiseGradientDensity` の `quarterNegative`）。足される 3 次元のノイズは、地面を削るより盛る方に 4 倍効くので、`depth` が 0 の高さは本物の地表の平均より低い
- 地表の規則（`MaterialRule`）は `compile(MaterialRuleContext)` で組み立ててから `tryApply(x, y, z)` で使う。`MaterialRuleContext` のコンストラクタと `updateXZ`・`updateY` は package-private。`MaterialSystem.topMaterial` は public だが、呼ぶたびに組み立て直す
- バイオームの地物は `Biome.getGenerationSettings().features()`（段階ごとの `PlacedFeature`）。`PlacedFeature.getFeatures()` は、選んで置く地物（`RandomSelectorFeature` など）の中身も並べる。置く数は `RepeatingPlacement.count`、何回に 1 回かは `RarityFilter.chance` で分かる
- ブロックのタグの `DIRT` は土だけ（草ブロックは `GRASS_BLOCKS`）。木が生える地面は `SUBSTRATE_OVERWORLD`
- vanilla のクラスをソースで読むには `./gradlew :<mod>:genSources`（`.gradle/loom-cache/minecraftMaven/` に sources の jar ができる）
- クラスの確認は `~/.gradle/caches/fabric-loom/minecraftMaven/net/minecraft/minecraft-merged-deobf/<MC>/*.jar` を javap する
